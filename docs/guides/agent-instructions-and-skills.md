# AGENTS.md 与 SKILL.md：项目规则和任务能力的边界

MirageFS 不只希望代码能够运行，也希望读者能够理解一个工程项目如何把
“长期规则”和“按需工作流”交给 AI Agent。`AGENTS.md` 与 `SKILL.md`
都在影响 Agent，但它们解决的是两个不同的问题：

```text
AGENTS.md：在这个目录范围内，始终应该遵守什么？
SKILL.md：遇到某一类任务时，应该怎样完成？
```

最短的判断方法是：

> 不管当前做什么都必须遵守的内容放 AGENTS；只有某类任务才需要加载的
> 方法放 SKILL；给人阅读的原理和教程放 docs。

## 通用设计意图

不同 Agent 产品对文件名、继承顺序、frontmatter 字段和触发算法的支持可能
不同。本指南讲的是 MirageFS 当前采用的设计模型；迁移到其他工具时，应先
查该工具的官方说明，不能只因为文件也叫 `AGENTS.md` 或 `SKILL.md` 就假定
行为完全相同。

### AGENTS.md：作用域内的常驻约束

`AGENTS.md` 是仓库或目录范围内的 Agent 说明。Agent 进入其作用域后，
不需要用户再次点名，这些约定就应当生效。

它适合保存：

- 项目身份和重要背景。
- 所有任务都必须遵守的安全或协作规则。
- 仓库级工作约定，例如是否允许自动提交。
- 指向更详细规则、文档和 skill 的路由。
- 少量无法从代码结构直接发现的全局事实。

它不适合保存：

- 某个偶发任务的完整操作步骤。
- 几百行语言编码规范或 API 手册。
- 只有调试、写作或发版时才用到的工作流。
- 可以从正式文档链接过去的大段教学内容。

大型仓库可以在子目录放置更具体的 `AGENTS.md`。这类文件通常只覆盖其
目录子树，并对根级规则做局部补充。规则越靠近目标文件，作用域越具体；
但不应复制根文件的全部内容，否则两份规则很快会漂移。

### SKILL.md：按任务加载的能力包

`SKILL.md` 是一个可发现、可触发的任务工作流。它通常位于一个独立目录，
并通过 frontmatter 描述名称和触发条件：

```yaml
---
name: diagnose
description: 在用户报告 bug 或性能退化时运行纪律化诊断流程。
---
```

description 的职责是帮助 Agent 判断“现在要不要加载这个 skill”。正文的
职责是告诉 Agent“加载以后怎样工作”。skill 目录还可以包含：

```text
skill-name/
├── SKILL.md
├── references/     # 按需读取的详细资料
├── templates/      # 可复用模板
└── scripts/        # 确定性的辅助程序
```

它适合保存：

- 有明确触发条件的工作流，例如诊断、TDD、代码评审。
- 特定领域的专业规则，例如 MirageFS 的模块边界和错误模型。
- 完成任务所需的步骤、检查表和验收方式。
- 只在该任务中需要的模板、参考材料或脚本。

它不适合保存：

- 每次任务都必须执行、却没有可靠触发条件的安全规则。
- 只对某个目录有效的简单约定。
- 项目成员需要持续阅读的完整教程。
- 与 description 无关、不断膨胀的“万能知识库”。

## 两者如何协作

二者不是互斥关系，而是常驻策略与按需能力的组合：

```text
用户请求
   │
   ├─ 读取作用域内 AGENTS.md
   │      └─ 得到项目身份、始终生效的约束和 skill 路由
   │
   ├─ 根据任务匹配 SKILL.md 的 description
   │      └─ 加载本次任务需要的专业工作流
   │
   └─ 读取代码与 docs
          └─ 获得当前实现和面向人的设计说明
```

例如用户说“诊断 rename 后偶发找不到文件”：

1. 根 `AGENTS.md` 告诉 Agent 这是 MirageFS 仓库，不能自动 commit。
2. bug 请求触发 `diagnose` skill。
3. 修改 MirageFS 代码又触发 `miragefs-core` skill。
4. Agent 从 `docs/modules/` 和源代码确认 NAMEI/FOPS 的真实边界。

这里 `AGENTS.md` 没有复制诊断循环，`diagnose` 也没有复制 MirageFS 的
全部架构；每份材料只负责自己的变化原因。

## 职责对照

| 维度 | AGENTS.md | SKILL.md | docs |
| --- | --- | --- | --- |
| 主要读者 | Agent | 执行特定任务的 Agent | 人，也可供 Agent 查阅 |
| 生效方式 | 进入目录作用域后常驻 | 用户点名或任务匹配后按需加载 | 主动阅读或被规则引用 |
| 典型内容 | 项目背景、安全和协作底线、路由 | 步骤、专业规则、模板、验收 | 原理、设计解释、教程、示例 |
| 理想长度 | 短，方便每次加载 | 主文件聚焦，细节可渐进展开 | 由教学完整性决定 |
| 变化原因 | 项目级工作约定变化 | 某类任务的方法变化 | 产品、架构或教学内容变化 |
| 错放风险 | 上下文常驻膨胀 | 不触发时关键规则失效 | Agent 不一定主动读取 |

## MirageFS 当前实现

### 根 AGENTS.md

根 [AGENTS.md](../../AGENTS.md) 负责整个仓库的常驻约定：

- 声明 MirageFS 是 C17 Linux 用户态文件系统模拟器和教学项目。
- 路由代码、架构和评审任务到 `miragefs-core`。
- 约定 `.cache` 任务总结的生命周期。
- 约定大任务提供 commit message，但不自动执行 `git commit`。

这些规则与具体任务无关，因此放在根 `AGENTS.md` 是合适的。

### miragefs-core skill

[miragefs-core/SKILL.md](../../.agents/skills/miragefs-core/SKILL.md) 是项目
特有的专业 skill。只要任务涉及 MirageFS 代码、架构、评审或设计，就必须
加载它。它负责：

- APP、Runtime、NAMEI、FOPS、Object、FSC、LSA 的依赖方向。
- C17 编码、命名、错误、日志、资源清理和并发规则。
- 公共 API、UT 编号、文档同步和评审检查点。

这些内容在写文章或整理 Obsidian 笔记时没有必要常驻，因此不应全部搬进
`AGENTS.md`。

### 其他 skills

`.agents/skills/` 还包含 `diagnose`、`tdd`、`review`、`prototype` 等通用
能力。它们是随仓库提供的工具箱，不是同时生效的项目政策。

有些通用 skill 源自其他技术栈，例如面向 TypeScript 测试的
`migrate-to-shoehorn`。文件存在只表示能力可被发现，不表示它适用于
MirageFS；只有任务确实匹配其 description 时才加载。

## 本次审计发现与修正

审计前，两类文件没有严重职责倒置，但存在以下问题：

1. 根 `AGENTS.md` 只有缓存和提交约定，缺少项目身份与 skill 路由。
2. `miragefs-core` 没有说明自己与 AGENTS/docs 的单一事实来源边界。
3. skill 把某台机器的绝对仓库路径写成固定规则，不利于其他学习者 clone。
4. 指南中没有解释“文件存在”和“规则已经生效”之间的区别。

本次已经补充路由和职责声明，并把仓库定位改为通过
`git rev-parse --show-toplevel` 动态发现。

## 新增规则应该放在哪里

可以依次问四个问题：

1. **它是否对这个作用域内的每一次任务都成立？**

   是：优先放 `AGENTS.md`。
2. **它是否只在某类任务中需要，并且有清晰触发条件？**

   是：创建或更新 `SKILL.md`。
3. **它是否主要帮助人理解原理、设计或操作方法？**

   是：放 `docs/`，再由 AGENTS 或 skill 链接。
4. **它是否只是当前会话的临时上下文？**

   是：不要污染前三者；放任务总结、issue 或临时工作区。

几个 MirageFS 示例：

| 新内容 | 推荐位置 | 原因 |
| --- | --- | --- |
| Agent 不得自动 commit | 根 AGENTS.md | 每次任务都成立 |
| 调试必须先构造复现闭环 | diagnose/SKILL.md | 只在诊断任务触发 |
| FOPS 上层必须走 dispatch | miragefs-core/SKILL.md | MirageFS 专业执行规则 |
| 为什么 FUID 不等于 inode | docs/modules/ 和 guides | 面向人的领域解释 |
| 本次 stat 改造验证结果 | `.cache/task-summaries/` | 有限生命周期的任务上下文 |

## 优先级、冲突与单一事实来源

最安全的维护方式不是在多处写同一句话，而是确定一份事实来源并从其他位置
链接过去：

- 常驻行为以作用域内 `AGENTS.md` 为入口。
- 任务流程以对应 `SKILL.md` 为入口。
- 项目架构事实以源代码和 `docs/modules/` 为准。
- 教学与操作说明以 `docs/guides/` 为准。

用户在当前任务中的明确要求通常高于仓库默认工作流。系统、平台或安全规则
仍可能具有更高优先级。遇到冲突时，Agent 不应静默选择，而应说明冲突、
采用的规则以及对结果的影响。

## 常见反模式

### 把 AGENTS.md 写成百科全书

结果是每次任务都携带大量无关上下文，规则难以发现，也容易和 docs 漂移。
AGENTS 应保持短小，通过链接完成渐进展开。

### 把安全底线只写进 skill

如果该 skill 没被触发，底线就不会生效。真正始终有效的规则应放 AGENTS。

### 为每条规则创建一个 skill

skill 应代表一个有内聚性的能力或工作流。过细会让触发选择比任务本身还
复杂。

### 把 docs 当成 Agent 自动配置

docs 是知识来源，不等于常驻指令。关键规则需要由 AGENTS 或已触发的 skill
明确路由到对应文档。

### 在多处复制同一规则

复制会制造多个“看似权威”的版本。应选择一个事实来源，其他位置只写摘要
和链接。

## 维护检查表

修改 Agent 相关文件时，可以使用下面的检查表：

- [ ] 这是常驻规则、按需工作流，还是教学文档？
- [ ] 文件的作用域和触发条件是否明确？
- [ ] 是否把个人机器路径或临时状态写进了可共享规则？
- [ ] 是否存在另一份重复且可能漂移的规则？
- [ ] 新 skill 的 description 能否独立判断触发条件？
- [ ] 长 skill 是否能把参考资料、模板或脚本渐进拆分？
- [ ] docs/guides 是否解释了对项目成员可见的工作方式？

正确划分后的目标不是“Agent 文件越多越好”，而是让每条信息只在需要时
出现，同时又不会漏掉真正必须遵守的约束。
